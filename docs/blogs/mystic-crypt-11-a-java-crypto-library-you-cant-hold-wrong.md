# mystic-crypt 11: A Java Crypto Library You Can't (Easily) Hold Wrong

*Symmetric and public-key encryption, password hashing, signatures, key agreement, and post-quantum cryptography, all behind an API where the footguns are already removed. Here's what it does, and what's new in 11.0.0.*

---

## The problem with "just use the JCA"

Java's built-in cryptography API, the JCA, gives you every primitive you need and almost no help using it correctly.

`Cipher.getInstance("AES")` compiles and runs, and silently gives you AES in ECB mode, which leaks the structure of your plaintext through the ciphertext. Reusing an IV with GCM doesn't throw an exception; it quietly destroys the authentication guarantee GCM exists to provide. Hashing a password with plain SHA-256 compiles too, and is the reason "we store hashed passwords" and "we store passwords an attacker can crack in an afternoon on a GPU" are sometimes the same sentence.

None of these are JCA bugs. They're footguns handed to every developer by default, because the JCA is a toolbox, not a set of decisions.

[**mystic-crypt**](https://github.com/astrapi69/mystic-crypt) is the opposite bet: small, focused classes that wrap the JDK's and [Bouncy Castle](https://www.bouncycastle.org/)'s primitives with the decisions already made. You pick the operation, encrypt this, sign that, agree on a key with this person, and the library picks parameters that aren't a trap.

```java
SecretKey key = SecretKeyFactoryExtensions
    .newSecretKey(AesAlgorithm.AES.getAlgorithm(), 256);

byte[] encrypted = new BaseByteArrayEncryptor(key)
    .encrypt("attack at dawn".getBytes(StandardCharsets.UTF_8));

byte[] decrypted = new BaseByteArrayDecryptor(key)
    .decrypt(encrypted);
```

That's AES-256-GCM, authenticated, with a fresh random nonce generated and prepended on every single call. There's no mode parameter to get wrong, because there's no mode parameter.

## What it actually covers

### Symmetric encryption

AES-GCM and ChaCha20-Poly1305, both authenticated, both with per-call nonce generation you don't have to think about. Works on byte arrays, strings, files, streams, and serializable objects. Chainable encryptor decorators if you need to layer transformations.

Key-committing AEAD is in there too, closing the "invisible salamanders" attack, where a single ciphertext can be crafted to decrypt to two entirely different plaintexts depending on which key opens it.

### Password hashing

Argon2id is the default and the recommendation: memory-hard, tunable, with salt and parameters embedded in the returned string so there's no second column to manage in your schema.

```java
PasswordEncryptor passwordEncryptor = PasswordEncryptor.getInstance();

String stored = passwordEncryptor
    .hashPasswordArgon2id("correct horse battery staple");

boolean ok = passwordEncryptor
    .matchArgon2id("correct horse battery staple", stored);
```

PBKDF2-HMAC-SHA256, bcrypt and scrypt are also available, purely for interoperating with systems that already store those formats. Every comparison in the library, across every algorithm, is constant-time.

### Public-key cryptography

RSA hybrid encryption: RSA wraps a fresh AES key rather than encrypting your data directly, because raw RSA has both a size limit and sharp edges.

Ed25519 for signatures. X25519 for key agreement with the raw shared secret run through HKDF rather than handed to you directly. A raw ECDH output is not a key; treating it as one is another classic footgun this library closes.

Reading and writing PEM, DER and PKCS#8 keys generated by OpenSSL or by Java itself. X.509 certificate generation, keystore handling, and PKCS#11/HSM provider configuration for when the key material needs to live in hardware.

### Post-quantum cryptography

ML-KEM (FIPS 203) for key encapsulation, ML-DSA (FIPS 204) and SLH-DSA (FIPS 205, all twelve pure parameter sets) for signatures. Plus a hybrid X25519+ML-KEM combiner for the transition period, which stays secure as long as *either half* of the pair remains unbroken.

Nobody should bet their entire security model on a five-year-old post-quantum algorithm just yet. The hybrid combiner is the honest way to start moving.

### Hashing

SHA-2 and SHA-3 (both via the JDK directly, no third-party dependency needed), BLAKE2b and BLAKE2s including keyed MAC mode, plus file and object checksums.

### Secret sharing and password-authenticated key exchange

Shamir's Secret Sharing and Feldman's verifiable variant, where a dishonest dealer handing out a bad share gets caught by the receiver instead of silently corrupting the reconstruction.

J-PAKE and SRP-6a let two parties agree on a strong shared key from a weak shared password, without the password itself ever crossing the wire. AES key wrap for protecting one key with another.

### A command-line interface

Shipped as a runnable uber-jar:

```shell
java -jar mystic-crypt-11.0.0-all.jar \
    hash --password "correct horse battery staple"

java -jar mystic-crypt-11.0.0-all.jar \
    checksum --file build.gradle --algorithm SHA-256
```

`hash`, `verify`, `keygen`, `kem`, `checksum`, `der2pem`, `cert`, `obfuscate` and `disentangle`. The exit code is the result, stdout is the contract, so it composes into shell scripts the way a Unix tool should.

### Documentation as executable code

Every one of the code examples above runs as an actual test. [`ReadmeExamplesTest`](https://github.com/astrapi69/mystic-crypt/blob/develop/src/test/java/io/github/astrapi69/mystic/crypt/ReadmeExamplesTest.java) compiles and executes every snippet in the README on every build.

A documentation example that stops working is a build failure, not a support ticket three months later.

## What's new in 11.0.0

The headline change is the one that forces the major version bump: **the minimum required JDK moves from 21 to 25.** Published bytecode now targets JDK 25, which is a breaking change for anyone still on 21 through 24. The library is built against the matching majors of its own dependency stack, `crypt-api` 10.0.0 and `crypt-data` 11.0.0, so the whole chain moves together rather than leaving a mismatched link behind.

Everything else folds in a full cycle of new capability that two prior, never-released `-SNAPSHOT` versions had been accumulating:

- **The CLI and its uber-jar** are new outright. Previously this was a library you could only reach from other Java code; now it's also a tool you can pipe into a shell script.
- **SHA-3** joins the hashing lineup, straight off the JDK's own `MessageDigest`, no Bouncy Castle involved.
- **BLAKE2b and BLAKE2s** arrive with keyed (MAC) mode.
- **bcrypt and scrypt** join Argon2id for interop with systems that already store those formats. Argon2id remains the recommendation for anything new.
- **SRP-6a**, implemented directly against RFC 5054's reference math via Bouncy Castle's own `SRP6Util`, including the zero-public-value check both peers need to reject a specific active-attacker technique.
- **Key-committing AEAD** and **Feldman verifiable secret sharing** are both new.
- **A hybrid X25519+ML-KEM key exchange**, combining a classical and a post-quantum primitive so the pairing is only as weak as its strongest half.

None of that shipped as a bare feature dump. Every one of these went through the same testing discipline described in [the project's testing-strategy writeup](why-we-stopped-short-of-100-percent-mutation-coverage.md): not just "does it compile and pass a happy-path test," but mutation testing to check whether the test suite would actually *notice* if the implementation went subtly wrong.

That process caught real defects before they shipped: an AEAD class that threw on every single instantiation because of a constructor ordering issue, a secret-sharing implementation that silently split the wrong number due to an off-by-one, a convenience constructor that rejected every key handed to it. All fixed. All covered by a regression test proven to fail without the fix, before any of it reached a tagged release.

## Where it fits

mystic-crypt is the top of a three-repository stack: [`crypt-api`](https://github.com/astrapi69/crypt-api) defines the algorithm constants and interfaces, [`crypt-data`](https://github.com/astrapi69/crypt-data) provides the factories, key readers/writers and models, and mystic-crypt turns all of that into ready-to-use encryptors, signers and hashers. A [Swing desktop front end](https://github.com/astrapi69/mystic-crypt-ui) sits on top of the same library for anyone who wants a GUI rather than an API.

```groovy
implementation("io.github.astrapi69:mystic-crypt:11.0.0")
```

Full capability matrix, every algorithm, its class, and what's deliberately *not* implemented with the reasoning, lives in [`docs/CRYPTO_CAPABILITIES.md`](../CRYPTO_CAPABILITIES.md). The testing strategy and every surviving mutation-testing gap with its reason is in [`docs/TESTING.md`](../TESTING.md) and [`docs/COVERAGE_EXCEPTIONS.md`](../COVERAGE_EXCEPTIONS.md).
